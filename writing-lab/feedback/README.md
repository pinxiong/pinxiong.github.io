# 写作反馈闭环（每篇写完都必须走一遍）

> 目的：**文章不是终点，是下一篇文章的输入。**
> 每篇发布后都要产出一条可追溯的反馈记录，并把结论落进四个地方之一，不允许"读完数据，感慨一下，然后照旧写"。

## 一、三个时间点

| 时点 | 做什么 | 产出 |
|---|---|---|
| **D+0**（发布当场） | 登记发布台账：标题、渠道链接、发布时刻（GMT+8 与 UTC）、字数、代码块数、实验数量 | `PIPELINE_STATE.md` 一行 |
| **D+2**（48 小时后） | 归因：阅读/互动/评论逐条读，判断**读者在哪一段掉队、标题是否兑现、他们想要的下一篇是什么** | 本篇 `feedback/<date>-<uc>.md`（用 `TEMPLATE.md`） |
| **D+7**（满一周） | 趋势：与前三篇同渠道对比，看是文章本身的问题还是发布时点/选题的问题 | 追加进同一份记录 + 周一复盘汇总 |

小样本规则：发布不足 48 小时、或 Dev.to views < 50 时，只写"观察项"，不下结论、不改硬规则。

## 二、结论只能落到这四个出口

每条反馈必须选一个出口，写清楚选择理由。**"不改"也是一个合法出口，但要写为什么不改。**

| 出口 | 落到哪 | 典型触发 |
|---|---|---|
| **A. 写作规则** | `~/.workbuddy/skills/tech-article-writing/`（SKILL.md 或 references/），并在 [`ledger.md`](ledger.md) 记一笔 | 多篇重复出现同一类读者困惑；某个开篇/小节结构稳定拉高或拉低完成率 |
| **B. 系列选题** | `strands-in-action/PLAN.md`（版本号 +1）+ `engagement/topic-backlog.md` | 读者提出的问题是"系列缺口"而非"本篇没讲清" → 走插队机制（见下） |
| **C. 发布策略** | `strands-in-action/PUBLISHING-POLICY.md` | 连续多篇的时段表现与假设不符；某读者群明显接管了评论区 |
| **D. 不改** | 记录里写明理由 | 单篇波动、样本不足、与长期硬规则冲突 |

## 三、插队机制（读者反馈改变系列顺序）

这是本闭环最重要的一条，因为它是**读者直接改写计划**，不是修辞上的"听取意见"。

触发条件（满足任一）：
1. 同一个缺口被 2 位以上读者独立提到；
2. 读者追问的是"文章结论的边界"而不是"某个词的用法"（例如"崩溃在副作用之前怎么办"）；
3. 补齐这个缺口需要真实实验，而实验本身就能撑起一篇。

流程：`反馈记录 → PLAN 版本 +1（写清插在哪、原编号如何顺延、为什么值这个代价）→ 更新 PIPELINE_STATE.md 的下一批顺序`
约束：插队必须给出**顺延清单**，不允许只加不减、也不允许悄悄改编号。

## 四、追溯规则（硬性）

- `tech-article-writing` 里每一条硬规则，都必须能在 `ledger.md` 找到来源：要么一次真实读者反馈，要么一次实测数据。找不到来源的规则，下次复盘时可以删。
- 每条规则改动都记四要素：**日期 / 改了哪条 / 依据（评论链接或数据）/ 预期效果**。改完 2–3 篇后回看预期效果是否成立，不成立的撤回并写明。
- 反馈记录用中文写；引用读者原话时保留原文，不翻译、不改写（避免把读者的意思"顺"成我们想听的）。

## 五、文件

| 文件 | 用途 |
|---|---|
| [`TEMPLATE.md`](TEMPLATE.md) | 单篇反馈记录模板 |
| [`ledger.md`](ledger.md) | 写作规则变更台账（规则 → 依据 → 日期） |
| `YYYY-MM-DD-<uc>.md` | 每篇的实际记录 |
