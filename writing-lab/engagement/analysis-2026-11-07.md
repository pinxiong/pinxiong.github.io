# 反馈机制与首轮基线分析（2026-11-07）

## 机制怎么转

每小时一次 `scan.py`（定时任务「每小时文章反馈采集」）：

```
Dev.to API  ── views / reactions / comments + 评论正文（仅计数变化时才拉正文）
BC 页面内嵌 ── likesCount / commentsCount（评论正文是 JS，只有数量上升才开浏览器读）
Medium      ── 本机网络访问不了，手动项，不假装有数据
主站 Hugo   ── 静态站，无互动指标
       ↓
data/history.jsonl   每次追加，永不覆盖 → 趋势
data/latest.json     上次快照 → 环比 diff
data/dashboard.md    全量表格
data/new-comments.md 仅本轮新发现；无则 none
       ↓
有新评论 → 起草回复（源码行号 + 真实实验），绝不自动发布，交给 Pin 粘贴
```

规则：新评论必须「有出处 + 有实测」才回复；无新评论时任务只回一行简报，不写长文。

同一批文章、同样的写作标准，BC 上差出 **50 倍**。这不是内容质量差 50 倍，是分发位置差 50 倍。
含义：下一篇最值得优化的不是正文，而是**能不能被 BC 推荐**——封面、标题、首发时段、摘要前 100 字。

### 发现三：UC03 的 reaction 率异常高，值得复制其结构

UC03：62 views / **22 reactions**（35%）。同期其他篇 reaction 率 0–5%。
差异点：标题是反直觉断言（The Limits That **Don't** Limit），正文用实验推翻字面理解。
UC04 今天 4 reactions / 9 views，同属这一类。说明「反直觉标题 + 实测推翻」在 Dev.to 是有效的。

### 发现四：长尾搜索流量来自具体的操作性 how-to

2022 年的 VPC / EKS / ECS 三篇：3897 / 937 / 1037 views，是 2026 年所有文章的 10–100 倍。
它们不是写得更好，是**可被搜索的具体任务 + 四年累积**。
不必回头写 Terraform，但值得记住：一个能被搜索引擎匹配的具体问题，生命周期远长于机制讨论。

### 数据口径警告（不要过度解读）

- Dev.to `page_views_count` 有可疑行：Finding what broke 只有 4 views 却有 5 reactions。小样本不要排名。
- BC likes 不等于阅读；BC 不公开 views。
- Medium 完全没数据，任何「全渠道总量」都只是 Dev.to + BC。
- 单日数据看不出趋势，趋势判断一律用 history.jsonl 的多日对比。

## 发布节奏建议：每 2–3 天一篇，不要每天一篇

依据：

1. **数据不支持日更**。11-04 → 11-07 连续四天四篇，Dev.to views 15 / 39 / 62 / 9，没有随频率上升；
   UC01 只有 15 views，更像是发布当天没有获得任何分发窗口，而不是选题失败。
2. **成本不支持日更**。每篇的真实成本是：实验与证据（数小时）+ 正文 + 四渠道适配 + 评论回复。
   今天 UC04 的评论回复又各花了一轮实验。日更会首先牺牲掉「实测」这个核心竞争力。
3. **评论需要隔天照顾**。Reid 和 Alex 都是在发布后数小时到一天内出现的；日更意味着回复上一篇和写下一篇撞车。

建议节奏（一周 2–3 篇）：

```
D0  发布（四渠道 + Slack 文案）→ 当天两次看评论
D1  回复评论 + 把读者指出的真实缺口补回正文（UC03/UC04 都是这么变好的）
D2  下一篇的实验与证据；D2 或 D3 发布
```

另外每月可以插一篇「可被搜索的具体任务」型文章，用来养长尾，和机制类文章互不抢时间。
